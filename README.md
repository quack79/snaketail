# snaketail-net
A tail tool for monitoring text log files and Windows event logs

## Directory layout (convention)

| Path | Description |
|------|------|
| `src/` | Main program source and `SnakeTail.csproj` |
| `tests/` | Unit tests |
| `script/` | `build.ps1`, `publish.ps1`, `init_dev.ps1` |
| `.temp/` | Intermediate build files and output (redirected by the csproj; do not commit) |
| `.run/` | Local run working directory (`log/`, `config/`; do not commit) |
| `.dist/` | Local publish directory generated by `publish.ps1` (do not commit) |
| `0run.ps1` | One-step build, clean `.run/log`, seed `src\app.config` into `.run\config` (if missing), then launch or run tests |

For development, first run `.\script\init_dev.ps1` to initialize `.run` and run `dotnet restore`.

## Build

- A plain `dotnet build` (without an explicit `OutDir`) puts the intermediate files and default output of the main program, the test project and the `LongMaidDisplayPlugin` plugin project under `.temp/`.
- `.\script\build.ps1`: builds the main program and then the `LongMaidDisplayPlugin` plugin in `Debug` configuration; `SnakeTail.exe` goes to `.run\` and the plugin DLL to `.run\config\plugins\DragonMaid\`.
- `.\script\build.ps1 --release`: builds the main program and then the plugin in `Release` configuration; `SnakeTail.exe` goes to `.run\` and the plugin DLL to `.run\config\plugins\DragonMaid\`.
- The target runtime is fixed to `win-x64`; after the build, directories under `.run\**\runtimes\` other than `win` and `win-x64` are removed.
- The plugin directory is cleaned after the build, keeping only `LongMaidDisplayPlugin.*` and `s_skill.json`; main program artifacts such as `SnakeTail.*` are not kept.

Recommended VS Code extensions (see `.vscode/extensions.json`): **C# Dev Kit** (debugging, solutions and tests) and **C#** (language service and code analysis).

Run/debug: the working directory should be `.run/` (`0run.ps1` and the VS Code `launch.json` are already set up this way). Logs are written to `.run/log/`: `YYYY-MM-DD.log` (leveled line format) and `YYYY-MM-DD_crash.log` (unhandled exceptions etc.).

Startup config directory resolution (when restoring the default session at startup): `config/` under the working directory is preferred; if the working directory has no `config/`, it falls back to `config/` next to `SnakeTail.exe`.

## Polling and idle CPU

- Default polling parameters for file log windows: `FileChangeCheckInterval=500ms`, `FileCheckInterval=10s`.
- When an old session config is missing these or sets them to `<=0`, they automatically fall back to the defaults above, so the WinForms `Timer` doesn't drop to `100ms` and cause high CPU when idle.
- Log file change detection is "event-driven first + low-frequency polling as a fallback": `LogFileStream` receives directory events through `FileSystemWatcher` and only sets a change flag; the reader side triggers a check with a `200ms` debounce, reducing pointless IO while idle.
- The `FileCheckInterval` fallback check is kept to cover cases such as watcher buffer overflow, delayed/lost events on network drives, and out-of-order renames.
- At EOF the reader also does one lightweight resync against the underlying stream length: even if an event is missed, appended lines are read on a later tick.
- When opening multiple log files, each tab gets its own copy of the Tail config, so a shared config object can't cause "file monitoring to bleed into the last file".
- Fixed the tail read baseline when quick filter is on: the next line is now computed from the "unfiltered total line count", so the UI no longer goes a long time without refreshing after new content arrives.

## Automatic publishing (CI)
After changing the version in `src/SnakeTail.csproj` and pushing to `main`/`master`, the Version Release workflow creates a tag automatically. **For the Publish workflow to be triggered**, add a Secret under the repository's Settings → Secrets and variables → Actions:
- **Name**: `REPO_TOKEN`
- **Value**: a Personal Access Token (with the `repo` scope)

Without `REPO_TOKEN`, the tag is still created and pushed with `GITHUB_TOKEN`, but GitHub won't trigger Publish from that push; you can run Publish manually from the Actions page and enter the tag instead.

## Display plugins (TailForm)

- Scope: only the file log window `TailForm`; not extended to `EventLogForm`.
- Directory convention: `config/plugins/<plugin name>/`.
- Discovery: when the host starts or reloads config, it scans `*.dll` in each first-level subdirectory and looks for the first type implementing `ILogDisplayPlugin`.
- Menu behavior: a "Plugins" submenu appears in both the context menu and the main menu; the check order determines the plugin execution order.
- Missing config notice: if a plugin directory's DLL can be discovered but a required config file is missing when enabling it, the menu keeps the plugin and marks it "missing config"; checking it shows a dialog with the exact missing reason.
- State persistence: each file config saves `EnabledDisplayPlugins`; after a restart, opening the same config restores the enabled order automatically.
- Processing boundary: plugins only change the "display pipeline text" and text matching behavior; they do not change the raw log file, raw line numbers or the positioning model.

### Text behavior rules

- Based on processed text:
  - List display
  - Quick filter / inverted filter
  - Search (forward/reverse)
  - Quick highlight and configured keyword highlight
  - Hit counts and external tool triggers
  - Context menu "Copy (processed text)"
- Still based on raw text:
  - `Ctrl+C` (including shortcut copy after double-clicking to select a word in a line)

### Plugin trigger rules (including multi-line blocks)

- The plugin enable order semantics are kept: earlier plugins get the input first and decide first whether it is `Handled`.
- New optional block extraction: a plugin implementing `ILogDisplayBlockPlugin` can, after the current line matches, collect the complete text block that follows before entering `CanProcess/TryProcess`.
- When a block plugin is ordered first and successfully `Handled`, later single-line plugins do not process that input.
- When a block plugin returns multi-line text with the same number of lines as the input block, the host fills the display back line by line by raw line number, keeping a one-to-one "raw log line ↔ processed line" mapping.
- Plugins that don't implement the block extraction interface keep their original single-line behavior and are unaffected.

### Example plugin: DragonMaid

- Plugin directory: `config/plugins/DragonMaid/`
- Config files:
  - `s_skill.json`: reads `s_skill[*][0]=skill ID`, `s_skill[*][1]=skill name`
  - `s_battle_power.json` (optional): reads `s_battle_power[*][0]=key`, `s_battle_power[*][5]=name`
- Processing rules:
  - Single line: when `skills: <number>`, `passive_skill: <number>` or `aura_skills: <number>` matches and a mapping exists, it is shown as `key: <number> <skill name>`; unknown IDs (e.g. `passive_skill: 0`) are left as is.
  - Single-line list: when `skill: [<number>,<number>,...]` or `"skills": [<number>,<number>,...]` matches, the list is expanded item by item; known IDs are shown as `<number> <skill name>` and unknown IDs are left as is (e.g. `"skills": [2001 NameA,3002,4001 NameB]`).
  - Multi-line list: when a `"skills": [` (or `skills: [`) start is matched and collected up to `]`, each pure-number entry is expanded line by line to `<number> <skill name>`, keeping the original indentation and commas.
  - Multi-line block: when an `attr_data=effects {` start is matched and a contiguous `effects` structure block is collected, `key: <number>` is expanded to `key: <number> <name>` (e.g. `key: 1 HP`).
